**The one remaining real failure** (test at line ~122, `describe("gracefulShutdown — blocks on in-flight HTTP work")`, `it("does not resolve while a request handler is still running, and delivers the full response before teardown closes anything")`):

The test: starts a real Fastify app with a `/slow` route that blocks on a gate, fires a real HTTP request via `fetch()`, waits for the handler to actually start, then calls `gracefulShutdown(app, deps, log)` with `deps.closeServer = () => app.close()`. It asserts shutdown does NOT resolve while the request is still in flight (this part passes). Then it releases the gate, awaits the fetch response, and asserts `shutdownPromise` resolves within 2000ms of the response arriving (`assert.equal(resolved, true, ...)` at line 181) — **this is what fails**: `app.close()` (i.e. Fastify's own close, wrapping Node's `http.Server.close()`) does not resolve within that window even after the in-flight request has fully completed and the client has received its response.

This smells like the well-known Node `http.Server.close()` keep-alive gotcha: `server.close()` stops accepting new connections and resolves once ALL existing sockets close, but if the client (here, Node's built-in `fetch`/undici) keeps the TCP connection alive via HTTP keep-alive after receiving the response (which it does by default, to reuse the connection), the server-side socket may stay open indefinitely, and `close()`'s promise never resolves — even though the actual application-level request/response cycle is done. This would NOT be a bug in `shutdown.ts`'s logic; it would be a Fastify/Node HTTP keep-alive interaction that needs handling.

1. Confirm this diagnosis by testing directly: does the test pass if the fetch client explicitly disables keep-alive (e.g. `fetch(url, { headers: { Connection: "close" } })`, or using an undici `Agent` with `keepAliveTimeout: 0` / `pipelining: 0`)? If so, that confirms the keep-alive theory.
2. If confirmed, the real-world fix belongs in `shutdown.ts` / how the Fastify app is closed, not in the test — a k8s pod being SIGTERM'd needs to actually drain and exit, and can't rely on every client being keep-alive-disabled. Check whether Fastify or the underlying `http.Server` exposes a way to close idle/keep-alive connections without killing in-flight ones — Node 18.2+ has `server.closeIdleConnections()` (closes connections with no active request) and `server.closeAllConnections()` (closes everything immediately, including in-flight — too aggressive, would cut off the response). The correct fix is likely: call `app.close()` to stop accepting new connections, and separately call `server.closeIdleConnections()` once the in-flight request(s) finish (or right after initiating close, since it only touches idle connections, never active ones) so the keep-alive socket that's just sitting there doesn't block `close()`'s resolution forever.
